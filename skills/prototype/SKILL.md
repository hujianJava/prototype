# 可交互原型（生产同构体）

原型的双重身份：给老板演示的验证工具 + /implement 的 UI 权威基准。因此它必须是**生产同构体**，满足六条铁律。铁律的 why：老板改需求要改得快，coding agent 接手要零翻译损耗——这两条是用户对原型的第一优先级。

**职责边界**：本环节只产出原型——不创建、不更新 `docs/specs/` 下的任何文件，尤其不写 SPEC。需求澄清的结论落点是原型本身（页面、路由、交互、mock）与交付说明里标注的默认项，不落成需求文档。SPEC 的唯一出生点是 /spec-freeze（老板确认后），值得留的规则不会丢——冻结时会拿原型提交历史逐轮回放兜住。不要"顺手记下来"：猜测和半成品规则一旦落成文件，就会获得不属于它的权威。

## 六条铁律

1. **同栈同路由**：React + TypeScript + Vite + Tailwind CSS + shadcn/ui；路由结构 = 未来真实应用的路由。禁止单文件 HTML、禁止"图快"换栈。
2. **mock 隔离在数据边界**：所有数据访问收敛到 `src/lib/api.ts`（统一接口签名），mock 实现放 `src/mocks/`。页面组件禁止直接 import mock 数据。这样 /implement 时只替换这一层，页面代码原样复用。
   mock 数据的定义：**只有"生产中会来自服务端的数据"才放 mocks/**（列表、详情、生成结果等 API 响应）。纯静态产品常量（文案、预置灵感主题、固定选项清单）放 `src/lib/constants.ts` 或 `src/content/`——它们在生产中不变，放进 mocks/ 会误导 /implement 去替换它；评审工具（如主题切换器）的内部状态同样不进 mocks。
   mock 数据的量级：列表类数据用确定性生成（如 faker 固定 seed）而非逐条手写——一行 seed 换来数百条跨状态、跨角色的稳定样本：刷新不变（演示与验收截图可复现）、分页/筛选立刻有意义、边界样本自动出现。手写只适合字段强关联的少量特定样本（如演示某个指定详情对象）。
3. **组件从 shadcn 体系出发**，不引入其他组件库；图标用 lucide-react。当 DESIGN.md 的组件规格超出 shadcn 默认（玻璃拟态、多主题、特殊定制组件等），允许按 DESIGN.md 规格手写组件，但必须：集中在 `src/components/`、规格以 DESIGN.md 为准、并在 AGENTS.md 技术栈里如实声明（如"手写组件体系，规格源 DESIGN.md §4"），不要让 shadcn/ui 的声明名不符实。
4. **状态完备**：每个数据页面必须有 空态 / 错误态（含重试）/ 加载态 三态。SPEC 的验收标准一定会写它们，现在不做，验收时一定返工。三态优先做成全局机制而非每页手写：骨架里在应用入口集中声明一次请求层错误拦截（统一错误提示、会话过期跳登录、服务端错误跳错误页），配一组独立错误页（401/403/404/500），每个页面只需补自己的空态与加载态。
5. **遵循 DESIGN.md**：颜色、字体、圆角、组件样式一律从项目根 DESIGN.md 的 tokens 取值，不自由发挥。
6. **交互状态显式化（URL 即状态）**：列表的分页、筛选、排序、搜索等"刷新后应保留"的状态序列化进 URL，参数在路由文件用 schema 显式声明类型与兜底默认值（非法值静默回落，不报错）；纯 UI 态（行选中、列可见性）留在组件内并注释标明边界。判据一句话：**能发链接让老板直达的状态，就必须在 URL 里**。why：一次显式化喂饱四方——老板收链接直达具体筛选现场、/spec-freeze 拿路由 schema 当字段清单、/accept 直接构造 URL 当 Given、/implement 把 schema 文件原样搬走。

## 页面级模式（防隐式、防黑盒）

铁律管底线，以下是高频场景的定型做法，照用可防 AI 自由发挥：

- **对话框编排**：一个 feature 的全部对话框用极小 context 编排——context 只存 `open`（'add' | 'edit' | 'delete' | null 这类判别值）与 `currentRow` 两个状态；所有对话框集中在一个组件里统一挂载；触发方（行操作、工具栏按钮）只调 `setOpen('edit')`。禁止开关 props 层层透传，禁止配置驱动的"万能对话框"。
- **导航单源**：侧边栏与命令菜单（如有）共用一份显式导航数据文件，加菜单项只改这一处，不从路由隐式推导。
- **命名名实相符，魔法数字注明来由**：变量与文件名跟实际职责一致（状态样式映射就叫 statusStyles，不叫 callTypes 这类名不符实的名字）；`setTimeout(fn, 500)` 这类延时/阈值必须注释解释（如"等关闭动画结束后再清选中行"）。无来由的数字与无语义的命名是 /implement 接手时的暗坑。

## 流程

1. 先读项目 AGENTS.md 与 DESIGN.md。没有 DESIGN.md 的，先引导 /design 或 /project-init，不要裸写 UI。
2. 需求澄清一次问全：页面清单、核心流程、用户角色。拿不准的交互直接给合理默认实现，在交付说明里标注"我默认了 X，可改"——比反复追问体验好。澄清结论只做进原型，不落文档（见"职责边界"）。
3. 搭骨架（路由 + 布局 + mock 层 + 全局错误策略）→ 逐页面实现 → 对照六条铁律自查。
4. 启动并交付：`npm run dev -- --host`，把局域网可访问的 URL 给用户（老板演示用同一地址）。
5. 迭代轮：老板的反馈原话直接作为修改输入；每轮改完输出"本轮改了什么"清单 + 新 URL。改动尽量只动页面与 mock 数据，不动 api 签名；动了要显式说明。**每轮达到可演示状态就 git commit**（`prototype: <本轮摘要>`，摘要列出本轮改动与对应的老板反馈要点）——原型是 SPEC ui-baseline 的引用对象，长期不提交会让冻结基准悬空。
   **会话结束前必须提交**：哪怕本轮没达到可演示状态（老板还没看、还在改），也要把当前改动提交掉（并入本轮提交，或单独 `prototype: wip <摘要>`）。未提交的改动等于不存在：导出看不到、开发冻结时逐轮回放不到、换台机器就丢了。

## 完成判据（交付前自查）

- [ ] 路由覆盖所有页面，跳转闭环无死链
- [ ] 列表页的筛选/分页/搜索状态在 URL 里，刷新与分享链接不丢
- [ ] 每个数据页三态（空/错/加载）齐全，错误处理走全局机制
- [ ] mock 数据量足以演示（列表类固定 seed 生成，可翻页 ≥ 2 页，含边界样本）
- [ ] 无 console 报错
- [ ] 本轮改动已 commit（git 工作区对 prototype/ 干净）
