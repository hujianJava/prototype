# 标准原型项目（PM → 开发交接）

你的职责止于：**可点击、可运行、可追溯的原型项目**。SPEC 冻结（业务规则 + 验收标准 + 接口契约等技术取舍）、实现与验收是开发侧的事（/spec-freeze、/implement、/accept），不要越界。

交付后，开发会接手运行 /spec-freeze——他会拿本仓库的逐轮提交记录（含老板每轮反馈要点）做"逐轮回放"，把业务规则一条条问清楚。所以你的提交信息就是冻结时的重要输入。

## 交付契约（缺一不可）

1. **仓库结构**（/project-init 已生成，不要改约定）：
   - `AGENTS.md` — 无 `<...>` 占位符，技术栈/命令/目录与事实一致
   - `DESIGN.md` — 视觉唯一事实来源（/design 产出）
   - `prototype/` — React + TS + Vite + Tailwind + shadcn 应用；数据全部 mock，统一走 `src/lib/api.ts`，页面不直连 mock 文件
   - `docs/specs/` 保持为空——不写 SPEC（SPEC 由开发接手后 /spec-freeze 产出）
   - 不含：生产代码、真实接口调用、真实密钥/账号
2. **git**：工作区干净；提交轨迹清晰（`project-init:` / `design:` / `prototype:`）；**每轮原型提交信息必须含"改了什么 + 老板反馈要点"**（冻结时逐轮回放的唯一线索）
3. **可运行**：新克隆环境 `cd prototype && npm install && npm run dev -- --host` 能起，页面可点、空/错/加载三态齐全
4. **交互状态**：列表分页/筛选/搜索等"刷新后应保留"的状态在 URL 里（刷新与分享链接不丢）

## 你是 PM 的唯一入口（先路由，再执行）

产品经理只需要记住本技能。每次会话先判断他当前要做的事，加载对应技能：

| 用户要做的事 | 调用 | 说明 |
|---|---|---|
| 新建原型项目 | `/project-init` | PM 固定答案：纯前端、无后端、无现有系统、React + TS + Vite + Tailwind + shadcn |
| 定风格 / 换风格 / 改设计规范 | `/design` | 之后每次改 DESIGN.md 或视觉风格都走它 |
| 新增或修改原型（页面 / 交互 / mock 数据） | `/prototype` | 之后每次原型改动都走它 |
| 交付给开发 | 本技能的交付契约与自检 → `/prototype-export` | 推送远端或导出含历史的 bundle |

路由后以被调用技能的规则为准执行；本技能的契约与边界始终生效（不写 SPEC、不写生产代码，冻结/实现/验收属开发侧）。

## 整体流程（从零到交付）

1. `/project-init` — 新建项目。PM 场景的固定答案：纯前端、无后端、无现有系统、React + TS + Vite + Tailwind + shadcn。
2. `/design` — 选风格 / 复刻参考风格；公司已有 DESIGN.md 基线就直接复用。你也是 UI，视觉把关在这一步。
3. `/prototype` — 对话迭代原型，每轮可演示就 commit（摘要含老板反馈要点）；老板用局域网 URL 直接点，反馈原话直接转给 AI 改。
4. 交付 = 调用 `/prototype-export`：推送到共享 Git，或导出含完整历史的 git bundle；然后发交接消息（模板见下）。到此为止，不要跑 /spec-freeze、/implement、/accept。

**改动归属（硬规则）**：原型页面的任何新增/修改都必须通过 `/prototype`；`DESIGN.md` / 视觉风格的任何调整都必须通过 `/design`。不要绕过技能直接改文件——mock 数据边界、三态要求、每轮提交、设计 tokens 约束都由技能承载，跳过技能这些保证全部失效。

## 交付前自检（逐条打勾，不过不交）

- [ ] `git status` 干净；`git log` 每轮提交都带"改动 + 老板反馈要点"
- [ ] 重新克隆仓库后原型能按命令启动（不依赖你机器上的残留环境）
- [ ] 三态（空/错/加载）抽查通过；列表页筛选/分页状态在 URL 里
- [ ] AGENTS.md / DESIGN.md 无占位符、无真实凭证
- [ ] `docs/specs/` 为空（没有 SPEC 草稿）
- [ ] 老板已经点过最新一轮原型，反馈已全部做进原型

## 交接消息模板（发给开发）

> 原型项目已就绪：<仓库地址>（分支 <branch>，最新提交 <hash>）
> 原型运行：`cd prototype && npm install && npm run dev -- --host`
> 老板反馈轮次：共 <N> 轮，均已包含在提交信息里
> 已确定的业务规则/默认取舍：<1-3 条>
> 待开发确认的技术点：<接口字段/错误码/权限实现等，1-3 条>

## 边界与变更

- 不写 SPEC、不碰 `docs/specs/`；SPEC 冻结由开发接手后完成（你可以参与回答业务规则）。
- 不写生产代码；不运行 /spec-freeze、/implement、/accept。
- 不修改 skills 仓库；有改进建议提给开发，由他回填。
- 交付后的仓库历史不要 rebase / force-push / amend——开发会基于它打冻结 tag。
- 老板在交付后改需求：先通知开发，由开发走 SPEC 新版本流程，不要自行改旧版本。
